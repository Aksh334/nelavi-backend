- **Orchestration runner (2026-10-18 record; Milestones 1B and 1D; `ARCHITECTURE_DECISIONS.md` OR-1):** added `orchestration/run.py` and `tests/test_orchestration.py`. `execute_run` validates one Record, then runs an explicitly supplied, ordered list or tuple of `Step`s: a step runs only if the steps it declares as dependencies completed, otherwise it is `skipped`; independent steps still run after a failure. Run statuses are `completed`, `partial`, `skipped`, `failed` and `invalid_record`. A failed step keeps only a closed error code (never an exception message, type or traceback). Results are normalised through JSON. The run id is its own value, never derived from the Record; an optional storage id is labelled `local_store` (unique only inside its database) or `unavailable`. No persistence, retries, timeouts, cancellation, asynchronous execution or result-size limit exists (the size limit is deferred).

Report inputs (`origin`, `user`, `image_ref`) are checked before any provider is called, using the pipeline's own validation; a failed stage keeps sanitised provenance (implementation class name, whether the object was invoked, model, query, retrieval time, dropped count); a record and a run are checked for consistency, using a SHA-256 content fingerprint when the run came from `run_report`. No `photo_id` lookup, no Research Pro, no provider SDK, no network.
