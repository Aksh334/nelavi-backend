## Decision Record Format (for future decisions)

Use this format only for decisions actually made. Do not create entries or IDs in advance.

- **ID:** sequential, assigned when the decision is made (for example `ADR-0001`)
- **Date:** date the decision was made
- **Status:** Proposed / Accepted / Superseded / Rejected
- **Context:** the situation and constraints
- **Decision:** what was decided
- **Alternatives considered:** other options and why they were not chosen
- **Consequences:** what follows from the decision, including follow-up work
- **References:** the baseline documents, contract IDs, commits or reports that support it

### MD-3: Canonical readings
- **Related open items (remain open in the frozen contract):** R-13, R-1 (units).
- **Source/contract requirement:** the build document lists the sensors (NPK probe, capacitive moisture, DS18B20 soil temperature, BME280 air temperature, humidity and pressure, battery voltage divider, BH1750, and a Rev 7 battery DS18B20). The coding overview says NPK probe values pass through the calibration correction before the rules see them. Which readings the record holds is not defined.
- **Implementation decision:** `soil` has `nitrogen`, `phosphorus`, `potassium`, `moisture`, `temperature`; `air` has `temperature`, `humidity`, `pressure`; `battery` has `voltage_v`. NPK values are raw readings; no calibrated NPK fields are added. BH1750/light and battery temperature are **not** part of this Record Core. This is an implementation-scope decision only: it does not claim those sensors do not exist or can never be represented elsewhere, and the frozen source is unchanged. A reading is a finite JSON number or `null` (unavailable); NaN and infinity are rejected. `voltage_v` is the battery voltage in volts. No other reading carries a unit.
- **Still open:** R-13 (which readings the contract record holds, raw versus calibrated NPK, units).
- **Alternatives considered:** calibrated or raw-plus-calibrated NPK; including light and battery temperature.

### MD-4: Sensor status and leaf fields
- **Related open items (remain open in the frozen contract):** R-7, R-8.
- **Source/contract requirement:** the coding overview section 2: "Each sensor has a status flag, so one failure never blocks a record." The `LEAF <class> <conf> <photo-id>` line carries the class, confidence and photo ID together (section 1). The flag values and the effect of a camera failure on the record are not defined.
- **Implementation decision:** `sensor_status` has exactly `npk`, `moisture`, `soil_temperature`, `air`, `battery`, each exactly `"ok"` or `"fault"`; no other value is accepted. All canonical fields are present. An unavailable numeric reading is `null`. A sensor flagged `"fault"` may have its associated readings `null` or a finite number; both are valid. A sensor fault never by itself makes the record invalid, and a sensor fault is not a machine fault or machine health state. A sensor flagged `"ok"` must have finite numeric readings, so `"ok"` with a `null` reading is invalid (intentional). The owner confirmed these two interpretations on 2026-10-07. Mapping: `npk` to the three NPK readings, `moisture`, `soil_temperature`, `air` to the three air readings, `battery` to `battery.voltage_v`. `leaf_label`, `confidence` and `photo_id` are either all populated or all `null`. No camera status field is added. `"unclear"` is an ordinary non-empty `leaf_label`.
- **Still open:** R-7 (status-flag set and encoding, missing-reading representation) and R-8 (camera failure effect).
- **Alternatives considered:** omitted readings; a three-state flag; a camera flag.

### MD-5: Confidence scale (Record Core field only)
- **Related open items (remain open in the frozen contract):** R-9. A-10 and any other `conf` field are not affected.
- **Source/contract requirement:** the coding overview section 3 states the "unclear" thresholds as "70%" and "20 points". It does not define a scale for the confidence field.
- **Implementation decision:** `confidence` is a number from 0 through 100 inclusive. Values below 0 or above 100 are invalid. `confidence` may be `null` only when `leaf_label` and `photo_id` are also `null`.
- **Still open:** R-9 for the contract, A-10, and the scope of "unclear" (R-10, R-11).
- **Alternatives considered:** 0 to 1; unconstrained.

### MD-6: Validation policy
- **Related open items (remain open in the frozen contract):** R-1 (validation).
- **Source/contract requirement:** only "one failure never blocks a record" (coding overview section 2). Handling of invalid records and unknown fields is not defined.
- **Implementation decision:** the validator (1) rejects a record when a required structural, type or value rule fails, (2) collects all applicable errors, (3) rejects unknown fields at every validated level, (4) treats sensor faults as valid record content, (5) treats `"unclear"` as an ordinary valid label, (6) returns a valid record only when all rules pass, (7) does not modify its input, and (8) uses no network, file system, database, clock, calibration or hardware access. It remains a pure validation component.
- **Still open:** R-1.
- **Alternatives considered:** accept with warnings; mark offending readings invalid; ignore or preserve unknown fields.

## Storage Decisions: Prototype Historical Record Store (ST-1 to ST-3)

**Status of all three entries: Accepted.** Each is an **Owner-approved implementation decision**, approved on 2026-10-07 after the Storage + Historical Data pre-implementation review. They apply to the prototype historical Record store only. **Frozen contracts remain unchanged; their underlying open items remain open.** Nothing here resolves R-2, R-3, R-4, R-5, R-6, R-12, R-15, R-16, W-10, W-11, W-13 or any other frozen open item.

**Identifiers.** `ST-1` to `ST-3` follow the same smallest-numbering approach as `MD-n` and `MR-n` and are not contract IDs. Each entry separates the SOURCE REQUIREMENT, the OWNER-APPROVED IMPLEMENTATION DECISION and the REMAINING OPEN CONTRACT ITEMS.

### ST-1: Storage technology and location
- **Status:** Accepted. Owner-approved implementation decision.
- **SOURCE REQUIREMENT:** records are stored on the rover in LittleFS until the phone confirms upload (coding overview section 2), and the phone app queues them in IndexedDB (section 4). The frozen sources require no laptop-side or server-side store, no storage technology, and no historical query behavior.
- **OWNER-APPROVED IMPLEMENTATION DECISION:**
  - SQLite was selected as the prototype storage mechanism, using Python's standard-library `sqlite3` module. No third-party dependency is used.
  - `storage/` is the implementation package (`storage/record_store.py`, class `RecordStore`).
  - The database path is supplied by the caller, and `":memory:"` is supported. There is no default database file, and none is created inside the repository.
  - The schema has one table `records` with a storage-generated integer `id`, a `rover_id` text column and the canonical Record serialized as JSON text in `record_json`, plus an index on `(rover_id, id)`. There are no columns for `time`, `sequence_number`, `photo_id`, `confidence` or individual readings; the stored JSON is the source of truth.
  - A Record is validated by the existing Record Core validator before it is stored, and an invalid Record is rejected with the validator's errors and not stored. Each write is one atomic transaction.
  - This store is a prototype-side historical Record store. It does not replace the rover's LittleFS, the phone's IndexedDB, rover-to-phone upload synchronisation or any future production database.
- **REMAINING OPEN CONTRACT ITEMS:** R-15, W-10, W-11 (how Records arrive, and what "confirms upload" means), R-16 (storage-full behavior), R-5 and R-12 (identifiers stored as opaque values), R-6 (versions stored as given).

### ST-2: History semantics
- **Status:** Accepted. Owner-approved implementation decision.
- **SOURCE REQUIREMENT:** none. The frozen sources define no history ordering, uniqueness or retention rule. Open items bearing on this are R-2 (time), R-3 (sequence number) and R-4 (retry-safe unique ID).
- **OWNER-APPROVED IMPLEMENTATION DECISION:**
  - The store defines its own insertion-order history. The storage-generated row id is authoritative for storage ordering, and reads are in ascending id order (the latest-Record query returns the highest id).
  - Record time is not used for ordering, `sequence_number` is not used for ordering or uniqueness, and `rover_id` + `sequence_number` is not a unique key. Duplicate Records are allowed.
  - The only history operations are: filter by `rover_id`, `limit`, "after storage id" paging, and the latest Record. There are no time-range, sequence-number, sensor-value, photo, anomaly, machine-state or energy queries.
  - No deletion, retention, purging, upload confirmation, synchronisation or storage-full behavior is implemented.
- **REMAINING OPEN CONTRACT ITEMS:** R-2, R-3, R-4, R-15, R-16, W-11, W-13.

### ST-3: Corruption policy
- **Status:** Accepted. Owner-approved implementation decision.
- **SOURCE REQUIREMENT:** none.
- **OWNER-APPROVED IMPLEMENTATION DECISION:**
  - A stored row whose JSON cannot be decoded, or whose JSON is not an object, raises an explicit storage-corruption error that identifies the storage row. Corrupted rows are never silently skipped or repaired.
  - For this purpose, stored text containing the `NaN` or `Infinity` literals is treated as undecodable, consistent with the rule that stored JSON must not permit them.
  - Historical reads do not revalidate stored Records against the current Record Core validator. The stored canonical JSON is the historical source of truth, so a later validator change cannot make old history unreadable.
- **REMAINING OPEN CONTRACT ITEMS:** none are resolved or closed by this decision.

## Machine State Decisions: Rover Operating State (MS-1 to MS-3)

Date: 2026-10-07. **Frozen contracts remain unchanged; their underlying open items remain open.** Nothing here resolves a frozen open item, and the states below are simulator-level definitions, not industrial-machine claims. `MS-1` to `MS-3` follow the same smallest-numbering approach as `MD-n`, `MR-n` and `ST-n` and are not contract IDs.

**Statuses are mixed on purpose.** MS-1 records what the owner specified in the milestone instruction and is Accepted. MS-2 and MS-3 contain semantics and an integration design made while building and are **Proposed** (owner review pending). Where MS-3 follows an explicit owner instruction, it says so.

### MS-1: Vocabulary, scope and what is not inferable
- **Status:** Accepted. Owner-approved implementation decision.
- **SOURCE REQUIREMENT:** the frozen sources define no machine-state vocabulary and no states. They describe rover-side safety mechanisms (obstacle stop at 25 cm, battery cut-off at 9.9 V, coding overview section 2) but do not map them to states. The accepted decision MD-4 states that a sensor fault is not a machine fault or machine health state.
- **OWNER-APPROVED IMPLEMENTATION DECISION:**
  - The state vocabulary is the owner-specified set: `unknown`, `off`, `starting`, `running`, `idle`, `overloaded`, `fault`, `maintenance`.
  - The implementation is the package `machine_state/` (module `machine_state/state.py`), Python standard library only, a pure domain capability: no wall clock, randomness, network, database or hardware.
  - Only evidence that exists in the current telemetry is used. No motor current, load, vibration, RPM, thermal or production evidence is invented.
  - `overloaded` is never produced. `fault` and `maintenance` are produced only from explicit inputs (a non-empty `fault_reasons`, or a declared maintenance mode); the Mock Rover supplies neither, so they are unreachable from it. These limits are documented in `NOT_INFERABLE_FROM_TELEMETRY`.
- **REMAINING OPEN CONTRACT ITEMS:** W-2, W-3, W-4, W-5 (what the rover does at a watchdog trip, obstacle stop, battery cut-off and while reversing) are not mapped to any state. R-7 (status-flag set) is unchanged.

### MS-2: Evidence, state meanings and precedence
- **Status:** Proposed (simulator-level; owner review pending).
- **SOURCE REQUIREMENT:** none. The Mock Rover telemetry provides `started`, `camera.homed` and `running` (the rover is moving or turning); these are simulator state (MR-1 to MR-6).
- **IMPLEMENTATION DECISION:**
  - Evidence: `started`, `homed`, `moving` (each True, False or not reported), plus the explicit `fault_reasons` and `maintenance_declared` inputs.
  - Meanings: `off` is "the rover reports it is not started"; `starting` is "started but startup homing is not complete" (the simulator's startup homing, MR-2); `running` is "currently moving or turning"; `idle` is "started, startup complete and stationary". These describe the rover, not an industrial machine.
  - Precedence, highest first: fault, maintenance, unknown (started not reported), off, starting, running, idle, unknown (insufficient evidence). Contradictory evidence (movement reported while not started) is `unknown`, not an error.
  - A result carries only the state and a reason that cites the evidence. No confidence value exists.
- **REMAINING OPEN CONTRACT ITEMS:** none are resolved by this decision.

### MS-3: Integration boundary
- **Status:** Proposed (simulator-level; owner review pending), except where marked as an owner instruction.
- **SOURCE REQUIREMENT:** none. The Record Core schema is frozen into the accepted decisions MD-2 to MD-6.
- **IMPLEMENTATION DECISION:**
  - Machine state is not added to the canonical Record, and the Record Core, Mock Rover and Storage are unchanged (owner instruction).
  - The evaluator consumes a Mock Rover telemetry snapshot through `evidence_from_telemetry`, which uses only `started`, `camera.homed` and `running`. It deliberately ignores sensor status, obstacle, battery, probe and link information, so those never change the state.
  - `machine_state` does not import `mock_rover`, `storage` or `record`; it only reads the shape of the snapshot.
  - An optional `previous_state` is echoed back with a `changed` flag. No transition is ever refused or constrained.

## Energy Monitoring Decisions: Rover Energy Calculations (EN-1 to EN-3)

Date: 2026-10-07. **Frozen contracts remain unchanged; their underlying open items remain open.** Nothing here resolves a frozen open item. `EN-1` to `EN-3` follow the same smallest-numbering approach as `MD-n`, `MR-n`, `ST-n` and `MS-n` and are not contract IDs.

**Statuses are mixed on purpose.** EN-1 records what the owner specified in the milestone instruction and is Accepted. EN-2 and EN-3 contain formula and integration choices made while building and are **Proposed** (owner review pending).

### EN-1: Scope and limits
- **Status:** Accepted. Owner-approved implementation decision.
- **SOURCE REQUIREMENT:** the frozen sources define no energy metrics, units, tariffs or production quantities. The build document lists design figures for the rover (3 x 18650 battery, "11.1 V, about 28 Wh", a 12 V 10 W solar panel, a charger at 12.60 V and 1.0 A); they are not telemetry and are not used as defaults. The canonical Record carries a battery voltage only. The Mock Rover telemetry provides battery `pct`, `voltage_v`, `charging`, activity `mode` and `sim_time`; it provides no power, current, capacity in watt-hours or solar rate.
- **OWNER-APPROVED IMPLEMENTATION DECISION:**
  - The implementation is the package `energy/` (module `energy/energy.py`), Python standard library only, pure and deterministic: no wall clock, randomness, network, database or hardware.
  - Only calculations justified by inputs that exist are implemented. No electrical, production, tariff or efficiency data is invented, and nothing is calculated when an input is unavailable.
  - Rover battery energy is kept distinct from machine electrical consumption and is never presented as it.
  - Elapsed time is only a supplied duration or the Mock Rover's simulated `sim_time`.
  - Deferred, not implemented: baselines and baseline deviation, peak demand, energy per unit or per kg, utilization, idle and startup energy, tariff schedules, and real voltage, current, power factor, frequency or cumulative-meter measurements.

### EN-2: Formulas, units and assumptions
- **Status:** Proposed (owner review pending).
- **SOURCE REQUIREMENT:** none.
- **IMPLEMENTATION DECISION:**
  - Units: power in W, duration in s, energy in Wh, tariff in currency per kWh. The only constants are 3600 s per hour and 1000 Wh per kWh. There is no default capacity, tariff or currency.
  - `energy_from_power`: Wh = W x s / 3600, for a supplied non-negative power assumed constant over the duration. No source feeds it yet; it is for future electrical measurements.
  - `battery_net_energy`: Wh = (pct_end - pct_start) / 100 x capacity_wh. This is an estimate that treats stored energy as linear in the charge percentage, uses a caller-supplied capacity, and is net of any charging (positive means net charge). It is not gross consumption.
  - `average_power_w`: Wh over elapsed hours. A zero duration is reported as an error, not as zero.
  - `energy_cost`: kWh x a caller-supplied tariff and currency, accepted only for energy from supplied power. Rover battery net energy is rejected because it is not billable consumption.
  - Results state their quantity, unit, duration, kind, source and assumptions. There are no confidence values or efficiency scores. Invalid or unavailable inputs raise errors; nothing is silently replaced with zero.

- **Status:** Proposed (owner review pending).
- **SOURCE REQUIREMENT:** none.

No state is assumed to imply any energy level (for example idle is not treated as inefficient, and off is not treated as zero energy). Utilization and idle or startup energy attribution are deferred, because their definitions are not established.

## Anomaly Decisions: Statistical Deviation Evaluation V1 (AD-1 to AD-8)

Date: 2026-10-08. **Frozen contracts remain unchanged; their underlying open items remain open.** Nothing here resolves a frozen open item. `AD-1` to `AD-8` follow the same numbering approach as the earlier decision groups and are not contract IDs. All eight are owner-approved implementation decisions (Accepted). The implementation is `anomaly/anomaly.py`.

**Source-supported facts used.** The frozen sources define no anomaly or deviation rule. The canonical Record carries no machine telemetry (no vibration, RPM, current, machine voltage, power, load or production quantity), no machine state, and no position. Baseline V1 (BL-1 to BL-8) provides a descriptive reference, and commit `1a274e2` exposed its per-observation classification as the public `classify_observation`, as a prerequisite to this work; that change added no rule.

**Frozen ambiguities that stay unresolved.** R-2 (time), R-3 and R-4 (sequence), R-6 (version provenance), R-13 (readings and units) and R-1 (validation ranges). V1 uses no time, sequence, version, unit or range, so it does not depend on them.

### AD-1: Scope and vocabulary
- **Status:** Accepted. Owner-approved implementation decision.
- **IMPLEMENTATION DECISION:** V1 is a deterministic, descriptive statistical deviation evaluation of one observation against a supplied descriptive reference. It is not machine-anomaly detection and claims no machine health, failure, failure prediction, fault diagnosis, cause, severity, maintenance recommendation, probability, confidence or RUL. The statuses are `within_reference`, `deviates_from_reference` and `not_evaluated`. Persistence, trend, EWMA, change-point detection, engineering-limit rules, relative (percentage) deviation and ML are not implemented.

### AD-2: Supported signals
- **Status:** Accepted. Owner-approved implementation decision.
- **IMPLEMENTATION DECISION:** only `air.temperature`, `air.humidity` and `air.pressure` are supported. The five soil signals and `battery.voltage_v` are rejected, because of the Baseline V1 caveats (position-confounded soil values; battery voltage that trends with usage). Any other signal is rejected.

### AD-3: Deviation and z-score
- **Status:** Accepted. Owner-approved implementation decision.
- **IMPLEMENTATION DECISION:** `deviation = observed_value - reference.mean`. When the reference spread is usable, `z_score = deviation / reference.std` (the reference's sample standard deviation). The observation deviates when `abs(z_score) > threshold`; equality is `within_reference`. The threshold is caller-supplied, finite and greater than zero, with no default. It is a configuration value, not a scientific claim.

### AD-4: Supplied reference
- **Status:** Accepted. Owner-approved implementation decision.
- **IMPLEMENTATION DECISION:** the caller supplies an existing `BaselineResult` for the same rover and signal; no baseline is computed during evaluation. The observation is classified with the public `classify_observation`, not by duplicated logic. As a best-effort guard, an observation whose storage id lies within the reference's `first_id`/`last_id` span is rejected. The guard is partial (the ids are those of the first and last supplied items, and may be absent); the caller remains responsible for the reference window.

### AD-5: Data quality
- **Status:** Accepted. Owner-approved implementation decision.
- **IMPLEMENTATION DECISION:** the observation reasons are those of `classify_observation` (`sensor_fault`, `null_reading`, `non_finite_or_non_numeric`, `invalid_record`, `wrong_rover`), and a fault flag takes precedence as it does there. An insufficient reference gives `insufficient_reference`. A reference `std` that is zero, or at or below the caller-supplied `min_spread` (finite, not negative, no default), gives `reference_has_no_spread`. In all these cases the status is `not_evaluated` and the result is never `deviates_from_reference`. No epsilon or other numeric default is used.

### AD-6: No windowing or temporal behaviour
- **Status:** Accepted. Owner-approved implementation decision.
- **IMPLEMENTATION DECISION:** no time-window, sequence-window, Storage access, persistence, consecutive-observation, sampling-gap or deduplication logic. The optional batch helper evaluates observations independently in the supplied order and carries no state between them.

### AD-7: Machine state
- **Status:** Accepted. Owner-approved implementation decision.
- **IMPLEMENTATION DECISION:** results are not grouped or conditioned by machine state. Machine state is not part of the Record, and the result context says it is unavailable.

### AD-8: Implementation boundary
- **Status:** Accepted. Owner-approved implementation decision.
- **IMPLEMENTATION DECISION:** the package is `anomaly/` (module `anomaly/anomaly.py`), Python standard library plus `baseline.baseline`. The result `DeviationResult` is a frozen dataclass with the approved fields only (`rover_id`, `signal`, `record_id`, `status`, `reason`, `observed_value`, `deviation`, `z_score`, `reference`, `threshold`, `comparison`, `unit`, `context`, `caveats`); the unit is `None` because units are unresolved (R-13). The code is pure, deterministic, non-mutating and independent of wall-clock time, randomness, network, files, database, hardware and providers. Baseline, Record Core, Mock Rover, Storage, Machine State, Energy and calibration behaviour is unchanged.
- **REMAINING OPEN CONTRACT ITEMS:** none are resolved by this decision.

## Image Analysis Decisions: NVIDIA Image Adapter V1 Transport Hardening and Size Limits (IA-5)

Date: 2026-10-12. **Frozen contracts remain unchanged; their underlying open items remain open.** `IA-5` follows IA-1 to IA-4 and extends IA-4 with a ninth error code. It is not a contract ID. It describes behaviour implemented in `image_analysis/nvidia.py` and `image_analysis/boundary.py` and covered by offline tests in `tests/test_image_analysis.py`. **IA-5 was approved by the project owner on 2026-10-13, as worded here.**

### IA-5: No redirects, local size limits and the ninth error code
- **Status:** Accepted. Owner-approved implementation decision (approved 2026-10-13). It describes behaviour that was already implemented in the code.
- **IMPLEMENTATION DECISION:**
  - **No redirects:** the default transport (`urllib_transport`) never follows an HTTP redirect. A 3xx response is returned to the adapter as an ordinary status. No second request is made, so the request body and the Authorization header are not sent to the redirect destination. `NvidiaImageAnalyzer.analyze()` reports any status outside 2xx, 4xx and 5xx (for example every 3xx) as `response_malformed`, when the response body does not trigger the oversized-body rule below (which takes precedence).
  - **Request size:** an image larger than `NvidiaConfig.max_image_bytes` is rejected as `image_unsupported` before it is base64-encoded, before the request body is built and before the transport is called. The default is 1 MiB (1,048,576 bytes of raw PNG, `DEFAULT_MAX_IMAGE_BYTES`). The value must be a positive integer (not a boolean); anything else makes the configuration `configuration_invalid`. This is a local resource-protection limit chosen by this project. It is not an NVIDIA limit and has not been tuned or checked against NVIDIA.
  - **Response size:** the default transport reads every response body, successful or an HTTP error, in bounded chunks. Each read request is capped at 64 KiB (`_READ_CHUNK_BYTES`) and at the number of bytes still allowed, so the adapter's own reads receive at most the limit plus one byte in total (a stream that honours the size it is asked for never returns more) and stop as soon as one byte beyond the limit has arrived. This bounds the adapter's own reads only; it does not control buffering inside Python's HTTP library. The limit is 4 MiB (4,194,304 bytes, `_MAX_RESPONSE_BYTES`), a fixed local limit that is not configurable and is not an NVIDIA limit. A body of exactly the limit is processed normally. A longer body is never silently truncated: it is reported as `response_too_large`, the ninth public error code, which `analyze()` returns instead of `provider_unreachable`.
  - **Precedence for HTTP errors:** if an HTTP error body itself exceeds the limit, `response_too_large` takes precedence over the status-based code. An error body within the limit keeps its status mapping (4xx `provider_rejected`, 5xx `provider_unavailable`, other non-success statuses `response_malformed`).
  - The public error set is now exactly nine codes: `credential_missing`, `configuration_invalid`, `image_unsupported`, `provider_rejected`, `provider_unavailable`, `provider_unreachable`, `response_malformed`, `response_empty` and `response_too_large`. The no-retry rule and the 60-second timeout default in IA-4 are unchanged.
- **Known limitations:**
  - A read failure, such as a timeout, part-way through a successful body is reported as `provider_unreachable`. A read failure part-way through an HTTP error body leaves an empty body, and the HTTP status alone decides the result.
  - In the Python 3.14.6 standard library source that was inspected, `HTTPResponse.read(n)` does not raise an error for a non-chunked response with a declared `Content-Length` when the connection ends before that many bytes have arrived: it returns what it has, and an empty read ends the body. A short body can therefore be returned, and this adapter adds no check for it. This conclusion comes from reading that source, not from a test that exercises the behaviour. Chunked responses and other Python versions were not inspected, and nothing here claims they behave the same way.
  - A body near the limit is briefly held in memory more than once while it is assembled (a list of chunks and then the joined result). This is qualitative reasoning from reading the code; memory use was not measured.
  - The behaviour was verified only on Python 3.14.6. No Python version is declared for the project.
- **Verification scope:** the behaviours described above were exercised by offline tests, using scripted streams, fake transports and, for the redirect tests, an in-memory fake HTTPS connection. Two statements were not established by a test: the Python standard-library statement comes from source inspection, and the memory-use statement comes from reasoning about the code. The adapter has not made a live NVIDIA request, so none of it has been observed against NVIDIA's hosted API, and successful inference through this adapter has not been established. PC-1 and PC-2 are unchanged: the two earlier HTTP 503 `ResourceExhausted` responses came from isolated image attempts outside the adapter, and the successful request recorded in PC-2 was a separate isolated-script request. No NVIDIA limit on image size or request size has been established.
- **REMAINING OPEN CONTRACT ITEMS:** none are resolved by this decision.

### OR-1: Orchestration runner (`orchestration/run.py`; Milestones 1B and 1D)
- **Status:** implemented and offline-tested (`tests/test_orchestration.py`, 37 tests passing on 2026-10-18).
- **IMPLEMENTATION DECISION:** `execute_run(record, steps, *, record_id, run_id, run_id_factory, clock)` is one synchronous function, not a framework, with no provider code, network, thread, queue or storage. `steps` must be a non-empty `list` or `tuple` of `Step(name, provider, call, depends_on, skip_reason)`; every Step is validated and copied into an immutable snapshot before the first step runs. Names, provider labels, skip reasons and error codes are lower-case tokens; a trailing newline is rejected.
- **Identity:** the run id is the caller's, a factory's or `secrets.token_urlsafe(16)`; it is never derived from the Record, and two runs of the same Record are two runs (no deduplication or idempotency is claimed). `record_id` is optional, a positive whole number, and means the caller-supplied local storage id: it is reported with `record_id_scope` `local_store` (the store assigns it per database, so it can only be compared within that one database; it is not a global or rover-wide identity) or `unavailable`. It is never inferred from `rover_id`, `sequence_number`, `photo_id` or `time`, none of which the frozen contracts make a unique key (R-3, R-4, R-12).
- **Semantics:** a step runs only if every declared dependency completed; otherwise it is `skipped` with `dependency_not_completed`. Independent steps still run after a failure. A step may also be skipped on purpose. Step results are normalised through JSON (tuples become lists, integer keys become strings, NaN and non-JSON values fail the step). Run status, in this order: `failed` if any step failed; `skipped` if every step was skipped; `partial` if some completed and some were skipped; `completed`; or `invalid_record` when the Record fails `validate_record` (no step runs, and the validator's `{path, code}` list is returned). An empty step list is a `ValueError`.
- **Errors:** a failed step keeps only a closed token (a `StepFailure` code if it is a lower-case token, else `step_failed`, or `result_not_serializable`). Exception messages, exception type names and tracebacks are never kept. Documented sanitiser limit: a deliberate `StepFailure` code or a step's returned result is stored as given, so step authors must use fixed, non-sensitive codes and return sanitised data.
- **Not provided:** retries, timeouts (a step that never returns blocks the caller), cancellation, asynchronous execution, persistence, recovery after a crash, or a result-size limit. A clock that fails or returns a non-string after the run has started aborts the call and the run is lost.

### OR-2: Offline report adapter (`orchestration/pipeline_steps.py`; Milestones 1L and 1N)
- **Status:** implemented and offline-tested (`tests/test_orchestration_pipeline.py`, 71 tests passing on 2026-10-18). Uses injected fakes only.
- **Why a bridge is needed (verified in the code):** the runner stores JSON, but `agri_pipeline.pipeline.run` reads `findings_result.status`, `.findings`, `research_result.items` and so on as attributes. The adapter stores the fields of the existing `FindingsResult` and `ResearchResult` as dicts and rebuilds the same dataclasses **by keyword** (a test checks every construction in the module); tests check that the rebuilt objects equal the originals and that the report equals a direct pipeline call for success, failure and skip combinations. The pipeline, the runner and the protected adapters are unchanged by this.
- **Inputs the caller must supply:** PNG bytes (no path is derived from `photo_id`, no file is read), the research query text, an optional `image_ref`, an optional storage id. Only the synchronous Tavily Search style `search(query)` is used; Research Pro (asynchronous) is not connected.
- **Stage outcomes:** missing provider, bytes or query, or an explicit skip reason: `skipped`, reported by the pipeline as `not_run`. Bytes that are not a PNG: failed `image_unsupported` without calling the provider. A provider error, an `unavailable` provider, findings that fail `validate_findings`, an unusable search result or a result JSON cannot hold: failed with a closed code, shown in the report as an image or research error with no findings or sources. Report codes are limited to the existing closed sets; any other code is shown as `response_malformed` and the exact code stays in `run["steps"]`.
- **Inputs checked before any provider call (1N, item A):** `check_report_inputs` runs the pipeline once with a harmless probe symptom, so the pipeline's own rules decide for `origin`, `user` and `image_ref` and no rule is copied. The order matches a direct call (origin, then the Record, then the rest). If the pipeline would report `invalid_input`, `run_report` returns the pipeline's own `invalid_input` report with the adapter-level run status `not_started`, `run` and `run_id` None, and no provider called. The adapter checks `image_ref` even when there are no image findings, which a direct pipeline call would ignore; `query` is not checked here (the research client checks it).
- **Failure provenance (1N, item C):** the runner keeps only an error code, so the step builders optionally fill a caller-owned `provenance` dict with sanitised facts: the configured implementation (module and class name), `provider_called`, the model (only short printable text), and for research the query, retrieval time and dropped count when the client's own result carries them. `provider_called` means the injected object's method was **invoked**; it does not show that a vendor was contacted (the real search adapter refuses `query_invalid`, `credential_missing` and `configuration_invalid` before sending anything, and a test shows `provider_called` true with no request). The implementation name is a Python class name, not a vendor claim. Nothing comes from an exception, a request or a provider response body. The model-text rule (non-blank, at most 128 printable characters) is this project's own sanitiser, not a contract rule. A failed stage's assembled result carries the model, query and retrieval time found there; nothing is invented when it is absent. Two unrelated things are called "provenance" in this module (the dict, and the text label copied from `FindingsResult.provenance`).
- **Record and run consistency (1N, item D):** `assemble_report` raises `ValueError` (fixed message, no values) if the run is not shaped like an `execute_run` result, if a run that executed steps belongs to an invalid Record (or the reverse), or if a supplied `record_sha256` differs from the Record's. `run_report` supplies that fingerprint: the SHA-256 of the canonical JSON of the validated Record. **Limits, stated and tested:** the fingerprint compares content only (equal Records have equal fingerprints) and is not an identity or a uniqueness guarantee; without it, two different valid Records cannot be told apart; `record_id` cannot be checked against the Record; `run_id`, `rover_id`, `sequence_number` and `photo_id` are not used as identity.
- **Behaviour changes to public functions (1N):** `assemble_report` now raises `ValueError` for malformed or provably mismatched runs where it previously returned a report, and its result has an extra `provenance` key.

## Security & Remote Exposure Decisions: M1 Backend Security Readiness (SE-1)

Date: 2026-10-24. **Frozen contracts remain unchanged.** Decision `SE-1` is an owner-approved implementation decision (Accepted). The implementation prepares the Python backend for future FlutterFlow web and mobile clients by establishing an explicit, opt-in remote-access layer while strictly preserving local-development behavior by default.

### SE-1: Opt-in remote server mode, Bearer-token authentication, CORS, health endpoint, and provider safeguards
- **Status:** Accepted. Owner-approved implementation decision.
- **IMPLEMENTATION DECISION:**
  - **Local mode default:** When launched without `--remote`, the backend retains all existing local-mode behavior: loopback-only default host (`127.0.0.1`), unauthenticated `/api/*` endpoints (with optional demo marker `X-Nelavi-Demo: 1`), local HTML/static UI enabled (`/` and `/static/*`), and 405 on `OPTIONS` requests.
  - **Explicit opt-in remote mode:** Remote mode is enabled only via `--remote`. It requires explicit `--host <ip/name>` and `--allowed-hosts <h1,h2...>`, and refuses to start (exit code 2) if `--allowed-hosts` is empty or missing, or if remote options are provided without `--remote`.
  - **Bearer-token authentication:** In remote mode, all `/api/*` endpoints require an HTTP `Authorization: Bearer <token>` header, evaluated using constant-time `hmac.compare_digest` to prevent timing attacks. The token is read from the process environment via the designated `--auth-token-env` terminal variable (default `NELAVI_AUTH_TOKEN`) strictly in `demo_app/server.py`. If the variable is unset or empty, the server refuses to start (exit code 2). The header `X-Nelavi-Demo: 1` is explicitly refused as authentication in remote mode (HTTP 401). The bearer token is never logged, echoed, or included in responses.
  - **Static web UI disablement (Option A):** In remote mode, static and HTML UI routes (`/` and `/static/*`) are disabled, returning HTTP 404 with JSON error details, preventing browser exposure of local-development UI files.
  - **CORS allowlisting and OPTIONS preflight:** Configured via `--cors-origins <origin1,origin2...>`. In remote mode, `OPTIONS` preflight requests for `/api/*` return HTTP 204 No Content with `Access-Control-Allow-Origin`, `Access-Control-Allow-Methods` (`GET, POST, HEAD, OPTIONS`), and `Access-Control-Allow-Headers` (`Authorization, Content-Type, Accept, X-Nelavi-Demo`) if the requesting `Origin` matches the allowlist, and HTTP 403 Forbidden if denied or missing. Wildcard origins (`*`) are strictly rejected during server startup validation (exit code 2). CORS headers are attached only to requests with allowed origins; CORS does not bypass authentication on actual API calls.
  - **Host header validation:** Host matching is case-insensitive per RFC 9110. In remote mode, hosts configured via `--allowed-hosts` automatically permit requests matching the host directly or with the server's listening port.
  - **Health check endpoint:** Minimal, unauthenticated `/health` (and alias `/api/health`) answering `GET` and `HEAD` requests with `{"status": "ok"}` (HTTP 200). Non-GET/HEAD methods return HTTP 405 Method Not Allowed. The endpoint performs no provider calls, checks no external networks, and exposes no secrets or configuration details.
  - **Remote real-provider safeguards:** Real provider stages (`nvidia`, `tavily`, `tavily-pro`, `openrouter`) are disabled by default in remote mode. Any request specifying real providers or stages without `--allow-remote-real-providers` is rejected with HTTP 403 Forbidden across all endpoints (`/api/run-integrated`, `/api/second-opinion`, `/api/advisory`, `/api/research-pro/start`). The CLI also fails closed on startup if real provider options are configured in remote mode without `--allow-remote-real-providers`.
  - **Request and connection limits:** Added client socket timeout `30.0` seconds and server timeout `30.0` seconds. Inactivity during body reading produces HTTP 408 Request Timeout. Bounded payload limits (up to 20 MiB for image endpoints, 2 MiB for text endpoints) are enforced before reading the request stream; malformed, negative, or non-digit `Content-Length` headers are rejected with HTTP 400. Limitation: an application socket timeout alone does not prevent all slow-client (Slowloris) attacks where data is dripped within 30-second windows; an external reverse proxy with transfer-rate enforcement is required for complete slow-client protection.
  - **Isolation boundary preserved:** `TestIsolation` was updated narrowly to allow `hmac` in stdlib and allow `server.py` to read `NELAVI_AUTH_TOKEN` from the process terminal variables. The absolute ban on provider credentials (`NVIDIA_API_KEY`, `TAVILY_API_KEY`, `OPENROUTER_API_KEY`) and live provider networking throughout `demo_app/` remains strictly enforced.

- **Evidence that prompted it (live smoke test, 2026-10-24):** A single live NVIDIA smoke test request using `scripts/nvidia_findings_smoke_test.py --send` with the verified real leaf photo (`Screenshot 2026-10-06 175858.png`, 232,255 bytes, SHA-256 `e87e04a4cb91b053...`) succeeded at Stage 1 (HTTP 200, 60.7 s, 119 tokens, 1,028 chars) but failed Stage 2 findings validation (`code: response_malformed`) with diagnostic `WRONG_TYPE at crop`.
- **Root cause analysis:** In `agri_pipeline/findings.py`, `build_prompt()` stated:
  `- "crop" is {"candidates": [...]}. "candidates" holds up to 5 objects, best guess first. Each has exactly the keys "name", "evidence" and "uncertainty".`
  And in the values section:
  `- null is allowed only for growth_stage.candidate. Everywhere else use a text or a list, and use [] when there is no supported information.`
  In English and agricultural usage, "crop" is an entity/crop name, naturally leading LLMs to output `"crop": "Tomato"` (a text) or `"crop": ["Tomato"]` (a list), reinforced by the sentence "Everywhere else use a text or a list". When `document["crop"]` is a string, list, or null rather than a JSON dict, `validate_findings` rejects it and `diagnose_findings` reports `WRONG_TYPE at crop`.
- **Prompt correction (narrow and minimal):**
  1. Clarified in Structure: `'- "crop" is a JSON object with exactly the single key "candidates" (never a string, list, or null): {"candidates": [...]}. "candidates" holds up to %d objects, best guess first. Each has exactly the keys "name", "evidence" and "uncertainty".' % MAX_CROP_CANDIDATES`.
  2. Clarified in Values: `'- null is allowed only for growth_stage.candidate. "crop" and "growth_stage" are always objects (never strings, lists or null). Everywhere else use a text or a list, and use [] when there is no supported information.'`.
  3. Strict validator integrity preserved: `validate_findings()` in `agri_pipeline/findings.py` is 100% strict and unchanged; malformed model replies are never coerced.
- **Constraints preserved:** Pure ASCII maintained (`prompt.isascii()`), prompt length bound preserved (`1500 < len(prompt) < 3000`, new length ~2,683 chars), all pinned prompt substrings preserved, and zero forbidden crop names or diagnostic words leaked.
- **Offline regression tests:** Added test cases in `tests/test_agri_pipeline.py`, `tests/test_nvidia_findings_smoke.py`, and `tests/test_nvidia_findings_rules.py` confirming:
  - Valid response with `crop.candidates` passes `validate_findings` and produces zero diagnostic errors.
  - String, list, or null at `crop` fails `validate_findings` and produces `("WRONG_TYPE", "crop")`.
  - Prompt assertions verify the exact prohibitions and object type requirements.
- **Verification:** Full offline test suite (`python -B -W default -m unittest discover -s tests`) ran with provider keys unset: **1,957 tests, OK, 17 skipped**. No live calls, no credit consumption, no server modification.

### FF-1: FlutterFlow Client Contract, OpenAPI 3.1 Specification, and Base64 Media Protocol (2026-10-25)
- **Status:** Accepted. Completed sprint implementation (Combined M2.1 + M2.2 + M2.3).
- **Context:** To connect FlutterFlow web and mobile applications with the CropSync / Nelavi backend, a formal client-facing API contract was established. The contract covers four core client screens: (1) Dashboard & Field Telemetry, (2) Multi-Modal Leaf Analysis & Diagnostics, (3) Agronomic Advisory & Voice Assistant, and (4) Precision Agriculture Learning Academy.
- **Decision & Architecture:**
  1. **OpenAPI 3.1 Specification (`docs/contracts/OPENAPI_SPEC.yaml`):** Created a comprehensive, self-contained specification documenting all 17 functional endpoints, `/health` and `/api/health` aliases, the `BearerAuth` HTTP security scheme, query/path parameters, and strict JSON schemas. All dataclass models across telemetry, findings, research, synthesis, and voice/learning were formally documented. Preserves the IA-13 prompt repair requiring `crop` to be an object with a `candidates` array (`CropFindings`, `CropCandidate`).
  2. **Image Ingestion Protocol (M2.3 Decision):** Evaluated multipart form-data vs JSON base64. Retained the existing base64 JSON payload design (`image_png_base64`). Adding multipart/form-data would require introducing unapproved stdlib parsers (`email`, `cgi`) into `demo_app/` (violating `TestIsolation` audit boundaries) or adding third-party dependencies. In FlutterFlow, converting `FFUploadedFile.bytes` to a base64 string is natively supported via standard one-line Dart custom functions. Retaining base64 preserves atomic request binding (image + telemetry + crop + question) and bounded memory guarantees (`MAX_IMAGE_BYTES = 20 MiB`).
  3. **Audio Ingestion Protocol:** STT (`/api/voice/transcribe`) accepts raw binary audio (`audio/webm`, `audio/wav`, `audio/mpeg`) in the HTTP request body. TTS (`/api/voice/synthesize`) returns JSON with base64-encoded MP3 audio (`audio_base64`).
  4. **Offline Contract Tests (`tests/test_flutterflow_contract.py`):** 25 automated tests with offline socket, DNS, and urllib tripwires verifying:
     - OpenAPI 3.1 specification syntax, paths, and component schema integrity.
     - Exact schema conformance across all 4 FlutterFlow screen workflows using actual `DemoApp` and `DemoService` handlers.
     - Remote Bearer token authentication enforcement and non-leakage.
     - CORS preflight `OPTIONS` status (204) and header matching.
     - Request body size bounds and validation error responses.
  5. **Client Integration Documentation (`docs/FLUTTERFLOW_INTEGRATION_GUIDE.md`):** Complete guide detailing base URLs, authentication headers, Dart custom functions for base64 conversion, screen mappings, CORS setup, and error matrices.
